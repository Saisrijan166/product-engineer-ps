Explain it to me

The problem, in one paragraph

Two companies' software needs to talk. Something happens in the first — an alert is raised — and the second needs to know immediately. The usual way is a webhook: the first system simply makes a web request to an address the second one gave it. That is easy when everything works.

It often doesn't. The receiving system may be restarting, or overloaded, or answering so slowly that we give up waiting. Any of those can last a second or an hour. The message still needs to get there, and nobody wants to find out days later that it vanished.

What this system does about it

It writes the message down before promising anything. The moment your app is told "accepted", the message is already stored. If every machine here lost power at that instant, the message would still be waiting when they came back.

It keeps trying, but not forever. Five attempts, with a growing pause between them, then it stops and records why. Growing pauses matter: hammering a system that is already struggling is how you keep it down.

It tells you exactly what happened. Every attempt is kept — when it went out, what came back, how long it took. That is the "full story" screen.

Why it doesn't retry everything

There are two kinds of failure, and treating them the same is a mistake either way.

Worth trying again: "I'm too busy", "something broke on my end", no answer at all, couldn't connect. These are usually temporary.

Not worth trying again: "that address doesn't exist", "I refuse to accept this message", "you're not allowed". These will fail identically in ten minutes, so this system stops at the first one — with four attempts left unspent. Retrying them would tie up capacity to learn nothing.

For engineers: retryable is 408 425 429 500 502 503 504 plus connect/read timeouts, connection refused, DNS failure and connection reset. Everything else that isn't a 2xx is permanent, including all other 4xx, 3xx (redirects are not followed), 501 and 505.

How long it waits

Each pause is longer than the last, so a system that needs a minute to recover gets one, without being poked constantly in the meantime.

In this demo1, 2, 4 then 8 seconds — short so you can watch it
In production5 seconds, 25 seconds, about 2 minutes, then 10 minutes

Each wait also gets a small random adjustment. If a hundred messages are all waiting on one system that comes back, you do not want all hundred arriving in the same instant.

If the receiving system says how long to wait — some do — that instruction is followed instead, within limits.

For engineers: min(base × multiplier^(n-1), cap) with ±20% jitter, written into next_attempt_at. A Retry-After header overrides it, un-jittered, clamped to [1s, cap].

The one promise it can't make

This system cannot guarantee a message arrives exactly once. Nobody can. If the receiving system files the message away and then the confirmation is lost coming back, we have no way to tell that apart from the message never arriving — and the only safe choice is to send it again.

So the promise is different: at least once, and always recognisable. Every attempt carries the same reference number, so the receiving system can spot "I've already dealt with this one" and ignore it. That reference is shown on the full-story screen.

For engineers: at-least-once, with a stable X-Idempotency-Key equal to the delivery id. Receivers should record it in the same transaction as the effect.

What the five steps actually are

  1. Your app makes one web request to say something happened.
  2. Saved safely — the message and the intention to deliver it are written down together, in one go. There is no moment where one exists without the other.
  3. Waiting its turn — it sits in a list of work due to be done, ordered by when it is next due.
  4. Sending — a worker picks it up and makes the request.
  5. Their system answers, or doesn't. Either way the result is written down before anything moves on.

For engineers: ingest commits webhook_event + outbox_dispatch in one transaction; a dispatcher hands it to the delivery service, which is idempotent on event_id. The delivery table is the queue — workers claim due rows with SELECT … FOR UPDATE SKIP LOCKED, so any number of instances can run without a coordinator. Attempts are counted before the request goes out, so the five-try limit survives a crash; an abandoned attempt is reclaimed by a sweeper.

Why there's no message broker

Systems like this usually add a dedicated queueing product. This one doesn't: the database it already needs does the job, because a queue is really just a list of work with times against it.

The first design did use one, plus a second system for coordination. Both were removed before any code was written — fewer moving parts, and a stronger guarantee, because the backlog now lives in the same place as the data and cannot drift out of step with it.
